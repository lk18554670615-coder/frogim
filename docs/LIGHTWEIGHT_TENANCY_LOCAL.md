## 结构

同一 Go 程序支持 `IM_MODE=standalone/platform/enterprise`。平台为一个 Go 进程，内置后台，只管理企业目录、全局身份、App 版本与操作记录。平台仅保存身份和各企业个人资料快照，不保存业务关系。客户端从平台获得企业地址及 60 秒单次授权，然后直接向企业兑换会话；业务流量不经过平台。

企业使用原 API、企业后台、悟空 IM 与现有插件、LiveKit、MinIO、PostgreSQL 和 Redis。资料同步、建号、头像复制和撤权逻辑都在现有 API 内，没有增加企业代理或常驻服务。A 与平台共用 PostgreSQL 实例的不同数据库；Redis A 的 DB1 给企业，DB0 保留给平台（当前平台只依赖 PostgreSQL，不要求 Redis）。B 使用独立数据实例与卷。控制端口 8443 仅在内部网络开放，双向 TLS 按企业身份核对；每个容器只挂载自身私钥。

通话信令通过企业 API 的 `/livekit/rtc` 校验会话代次、企业和呼叫状态，再连接私网 LiveKit。RTC 媒体仍直接传输。企业模式禁止登记绕过校验的 LiveKit 客户端地址，原生信令端口不可公网暴露。这样既没有平台业务转发，也没有新增通话服务。自建 LiveKit 移除参与者不能单独保证旧令牌失效，见 [LiveKit 官方说明](https://docs.livekit.io/frontends/reference/tokens-grants/)。

企业模式的下载返回企业 API 固定地址，每次读取验证媒体会话及企业代次，不向客户端返回切换后仍有效的 MinIO GET 签名。上传仍直传对象存储，完成及绑定须验证当前企业会话；切换后迟到的完成请求被拒绝。企业后台的历史缩略图使用限定路径的 HttpOnly 管理员 Cookie，经现有管理员权限校验，媒体签名地址本身不再授予企业访问权。单企业模式保留原行为。

## 使用规则

企业资料与历史各自保留。管理员从用户列表查看资料抽屉或发起切换，必须填写理由和确认。首次进入目标企业建立同 ID 的账号、复制头像；已存在的目标资料不覆盖。准备后撤销旧业务、媒体、IM、推送及通话，再提交归属版本。操作中暂停新登录。失败或确认丢失从“操作记录”查询并重试原操作，不重新发起，不自动回退或补偿。切回旧企业继续使用旧资料和历史。手机号只经平台修改，成功前保留旧唯一身份并预留新号码；密码重置和封禁同样先完成旧企业撤权。

客户端完整保存 API、IM、通话、媒体地址及配置版本，拒绝缺失、凭据夹带或版本回退的配置。续期发现企业变化时先清理旧页面、IM、通话、设备和媒体身份，再兑换目标企业会话；旧业务请求不会重放到新企业。管理员切换引起 IM 断连时查询平台归属；普通同设备替换仍退出，不抢回另一设备会话。操作待确认时仅等待管理员重试原操作，客户端查询不推进管理任务。

客户端平台凭据与企业凭据按用途区分，支持同域名及企业路径前缀；图片缓存和图片组件状态也按企业、用户隔离，企业头像的 HMAC 地址还须当前媒体会话。缓存和 SDK 数据库按企业与用户区分，迟到回调按身份代次拒绝。平台不可用时，有效的企业业务会话继续使用，新登录和续期失败。后台资料显示同步时间；未同步、同步失败或企业无法连接均明确提示。
